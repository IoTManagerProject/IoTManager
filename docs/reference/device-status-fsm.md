# Конечный автомат статусов устройств

> **Reference**. Логика — `_next_state` в `core/devices.py` (ранее в `app.py`).
> Папка устройства идентифицируется ключом `<имя> <id>`.

## Состояния

| Цвет | Значение |
|---|---|
| 🟢 Зелёный | Свежий multicast-пакет с совпадением имени и id устройства **ЛИБО** успешный пинг + актуальный `settings.json` с совпадением имени и id. Для свежего модуля без имени и id подтверждением считается отклик по его IP (см. правило ниже) |
| ⚪ Серый | Статус не подтверждён: пинг успешен, но multicast не приходил / имя+id не совпадают, или данных нет |
| 🟡 Жёлтый | 1–3 провала пинга **после зелёного** (multicast не обновлялся) |
| 🔴 Красный | Более 3 провалов пинга (только после жёлтого) |

Переходы реализует функция `_next_state(cur, fails, confirmed, ping_ok)`
(юнит-тесты — `test_device_status_fsm.py`).

## Ключевые правила

- Жёлтый/красный достижимы **только после зелёного**; из серого в жёлтый/красный перейти нельзя.
- Повторное подтверждение (multicast или пинг+settings) сразу возвращает зелёный.
- Успешный пинг без подтверждения переводит зелёный/жёлтый/красный в серый.
- **Живой multicast авторитетен над `settings.json`**: при свежем multicast пинг и
  `settings.json` НЕ выполняются (на разделяемом IP settings может вернуть имя другого
  устройства; после переименования остаются старые папки с тем же id).
- Пинг выполняется **один раз на уникальный IP**; если папок на одном IP несколько,
  он проверяется единожды.
- На одном IP зелёным может быть **только одно устройство** (`_enforce_single_green`):
  при обнаружении нескольких зелёных папок с одним IP зелёным остаётся подтверждённая
  в текущем цикле, остальные переводятся в серый (защита от дублей/коллизий).
- После свежего multicast устройство не пингуется **70 секунд** (`PING_SKIP_AFTER_MULTICAST=70`):
  multicast идёт каждые 60 сек и сам подтверждает живость и идентичность.
- **Узлы вне локальных подсетей панели пингуются редко.** Подсети всех IPv4-интерфейсов
  панели определяются по psutil (кэш 30 сек — переезд в другую сеть подхватывается сам).
  Если IP устройства не входит ни в одну локальную подсеть (панель переехала в другую
  сеть), каждая минута не тратится на subprocess-пинг: устройство сразу считается
  недоступным (переходы FSM — как при провале пинга), а полный пинг выполняется раз
  в 10 минут (`CROSS_SUBNET_RETRY=600`) — на случай доступности по маршруту (VPN,
  несколько интерфейсов). Если определить подсети не удалось (нет psutil), пинг
  ведётся как раньше.
- Во время скачивания файлов (`fetch` RAM/FS) пинг и WS-запросы к этому IP приостанавливаются
  (`_device_busy_fetching`), чтобы не срывать передачу.
- Источник идентичности при отсутствии multicast — `ws_client.fetch_settings(host)`
  (команда `/list|`, блок `settin`). Пинг (`_mark_device_seen`) НЕ обновляет
  `last_seen` multicast и зелёный не даёт.
- **Устройство без имени и id.** Свежий модуль в режиме точки доступа отдаёт пустые
  `name`/`id` (и в `/devlist.json`, и в `settings.json`), поэтому папка создаётся по
  IP (`<ip> <ip>`, вариант `name or ip` в `add_device_by_ip`), а кандидаты ключа
  строятся от IP (`_folder_key_candidates`, прежний вариант `unnamed <ip>` оставлен
  для совместимости). Подтверждением такого устройства считается отклик по его IP:
  multicast либо ping + `settings.json` с пустыми именем и id. Без этого правила
  безымянный модуль (например, найденный через WiFi-антенну панели на 192.168.4.1)
  оставался бы серым навсегда — при `_fetch_settings_identity`, вернувшем пустые
  имя/id. Если по этому IP откликнулось устройство с *другим* именем или id, папка
  остаётся серой (защита от подмены на переиспользованном адресе); в журнал пишется
  `Ping OK, no identity confirmation: <ip> (<key>), reported name/id: '<name>'/'<id>'`.
- **Папка «по IP» усыновляет имя и id устройства** (`resolve_identity_folder`).
  Порядок поиска папки, которую подтверждает отклик с IP: 1) точное совпадение ключа
  `<имя> <id>` (или легаси `<имя>_<id>`); 2) папка «по IP» (`<ip> <ip>`, легаси
  `unnamed <ip>`) — в неё записываются настоящие `name`/`id` (в `.device.json`);
  3) папка с тем же именем на том же IP, но другим id. Ключ и каталог на диске при
  этом **не меняются** — иначе после каждой перезагрузки модуля появлялась бы новая
  папка (у части прошивок id = `getChipId()`, он меняется при ребуте), а старая
  оставалась бы навсегда серой.
- Папку, в которой уже прописано **другое** имя, усыновление не перезаписывает
  (защита от подмены модуля на переиспользованном адресе); в журнал пишется
  `Identity adopted for folder '<key>': '<name>'/'<id>'`.
- Мультикаст подтверждает папку, полученную от `ensure_device_folder()`, даже если её
  ключ не совпал с ключом из пакета (папка «по IP», усыновившая имя/id) — иначе
  multicast завёл бы папку-дубль, а старая осталась бы серой.
- Имена устройств в вебе показываются без изменений (подчёркивания сохраняются) —
  в отличие от `dispName` проектов. Исключение — безымянные модули: папка
  `<ip> <ip>` (или легаси `unnamed <ip>`) в дереве подписывается просто IP, ключ и
  папка на диске при этом не меняются.
