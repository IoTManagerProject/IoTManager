# Changelog

Все заметные изменения репозитория IoTManager.
Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/).
Полная история: `git log --oneline`.

## [2026-10-07]

### Прошивка

- **Включена OTA прошивки для BK7231N (LibreTiny).** Раньше `upgradeBuild()` и
  `upgradeFS()` целиком вырезались для LIBRETINY (`#ifndef LIBRETINY`), поэтому все
  точки OTA (`/localota_handler`, WS `/update|`, `/update1|`) молча ничего не делали.
  Теперь в `upgradeBuild()` есть ветка LibreTiny: `HTTPClient::GET` → `Update.begin(size, U_FLASH)`
  → `Update.writeStream()` → `Update.end(true)` + перезагрузка — входной поток UF2
  (сигнатура «UF2\n»), как того ждёт `lt_ota_*` из beken-72xx. `upgradeFS()` для
  LibreTiny явно отключён с понятным сообщением и статусом `PATH_ERROR` в `ota.json`:
  `Update.begin()` в LibreTiny принимает **только U_FLASH**, поэтому OTA образа ФС
  невозможна в принципе (ФС — copy через `POST /edit` либо USB, таргет `flashfs`).
- `handleUpdateOTA()` (multipart `/update`): для LibreTiny `littlefs.bin` отклоняется
  с явной ошибкой 500 вместо невнятной «Недостаточно памяти».

### Панель magicIoTm

- **OTA: учёт LibreTiny в шагах.** `build_steps()` принимает `env`/`ini` и для
  LibreTiny-окружений (признак — `lt_fsbuild.py` в `extra_scripts`, как в
  `core/config.py`) отдаёт шаг `kind="error"` при `fs_method=flash` с `mode=fs|full`;
  воркер превращает его в `OtaError`, а `/api/ota/start` возвращает 400 до запуска
  воркера. `mode=full` для LT = copy (ФС) + pull `type=1` (прошивка).
- UI модалка OTA: для устройства `bk7231n` скрыты пункты «ФС: записать образ» и
  «Полная (образ ФС + прошивка)» + пояснение про copy/USB.

## [2026-10-05]

### Прошивка

- **BK7231N переключён на асинхронный веб-сервер** (ветка `bk7231n-async`).
  В `[env:bk7231n]` вместо `LT_WebSockets` подключены форки ESPHome
  (`esphome/AsyncTCP-esphome ^2.0.0`, `esphome/ESPAsyncWebServer-esphome ^3.0.0` —
  ESPAsyncWebServer 3.12.x не собирается на форке `Mit4el/libretiny`: `literals.h`
  требует `::emptyString`), стек AsyncTCP уменьшен до 4 КБ, очередь — до 32.
  Вариант (async/standard) выбирается единым переключателем `LT_ASYNC_WEB_SERVER`
  в `include/Const.h` (по умолчанию async); флагов `-DASYNC_*` нет ни в `bk7231n`,
  ни в ESP-окружениях (`[common_env_data].build_flags` очищен) — точечно вариант
  переопределяется флагами конкретного env.
  Сборка: flash 80,2 % (869 208 Б), RAM 36,6 % (95 924 Б). Поддержка LibreTiny
  появилась в ESPAsyncWebServer 3.7.8 (PR ESP32Async#187); прежний безусловный
  `#error` в `Const.h` заменён переключателем и гвардом от копирования `-DASYNC_*`
  из ESP-окружений. Детали: `docs/articles/async-web-server.md`, раздел 6.1.

- Правки кода под LibreTiny: `#include <WiFi.h>` в `include/Global.h` (раньше
  приходил транзитивно из `WebServer.h`); `send_P()` в `src/AsyncWebServer.cpp`
  для LIBRETINY идёт через `beginResponse_P()` — в esphome-форке нет перегрузки
  `send(code, contentType, const uint8_t*, len)`.

- **Upstream LibreTiny заблокирован**: в 1.13.0 нет `LittleFS` (его добавил форк
  `Mit4el/libretiny`), в реестре PlatformIO библиотеки тоже нет — остаёмся на
  форке `Mit4el/libretiny#master`. **Для LibreTiny нужен стабильный PlatformIO**:
  глобальный 6.2.1b2 (beta) роняет билд-скрипт платформы (`Library.__post_init__()
  missing 1 required positional argument: 'env'`); проверено на 6.1.18.

## [2026-10-04]

### Панель magicIoTm

- **Исправлен gauge FS = 0 % для платформы bk7231n.** Для LibreTiny образ ФС
  собирает кастомный таргет `tools/lt_fsbuild.py` и кладёт его как
  `lt_littlefs.bin` в корень проекта, а весь расчёт FS искал только
  `littlefs.bin`/`spiffs.bin` в `.pio/build/<env>/` — ёмкость получалась нулевой,
  и верхний индикатор «Файловая система» показывал 0 % (теперь, например,
  113 568 / 151 552 Б = 74,9 %). Образ ФС теперь ищется по обоим именам; для env
  с LibreTiny-ФС (признак — `tools/lt_fsbuild.py` в `extra_scripts` секции
  `[env:<env>]` файла `platformio.ini`) дополнительно проверяется корень проекта,
  так что образ чужой платформы не подставляется (`core/config.py`:
  `_is_lt_env`, `_fs_image_size`; `utils/build.py`: `_is_lt_env`, `_fs_total`;
  `measure_size/measure.py`: `is_lt_env`, `fs_image_size`, `get_fs_total`).
  В `platforms.json` для `bk7231n` записана ёмкость раздела `total_fs` = 151 552 Б
  (`0x25000`), поэтому базовый замер её больше не перезаписывает нулём.

- **WiFi: сбой подключения показывается сразу, а не через 25 с.** Во время
  ожидания ассоциации панель опрашивает журнал
  `Microsoft-Windows-WLAN-AutoConfig/Operational` (`wevtutil`, каждые
  `WLAN_FAIL_POLL` = 1,5 с) на событие `8002` с нужным SSID: как только Windows
  зафиксировала отказ (нет сети, неверный пароль), причина из `FailureReason`
  сразу уходит в `connect.error` — полное `CONNECT_WAIT` не расходуется
  (`core/wifi.py`: `_wlan_connect_failure`, `_wait_ssid(since=…)`). Если журнал
  недоступен (не Windows, права) — прежнее поведение с таймаутом.
- **Ошибка подсети модуля стала понятной.** Вместо «Адрес панели (…) не входит
  в подсеть модуля 192.168.4.0/24» (со списком всех интерфейсов, включая 16+
  адресов `169.254.*`) сообщение теперь: что нужен адрес `192.168.4.x`, какие
  у панели реальные адреса, сколько адресов APIPA (`169.254.x.x` — DHCP не
  отвечает) и вероятная причина — панель не в сети модуля.
- **Модалка с фиксированной шириной.** `.modal` — `width: 500px` вместо
  `min/max-width`, ширина окна больше не «дышит» от содержимого (на узких
  экранах — `max-width: 95vw`).
- **Убрана подсказка «модули iotm* — впереди»** из заголовка модалки WiFi:
  `<h3>📶 Сети WiFi</h3>` (сам порядок списка не изменился).
- **WiFi-модалка: показ всех сетей эфира (модули `iotm*` — впереди).** В состояние
  сканера добавлено поле `all` — все видимые сети, где точки доступа модулей идут
  первыми (внутри групп — по убыванию сигнала, у каждой записи флаг `iotm`);
  `networks` по-прежнему содержит только AP-сети модулей (по ним считаются `new`,
  `alert` и прогрев кнопки «!»). Модалка показывает `all`, поэтому подключиться
  теперь можно и к обычной сети (`core/wifi.py`, `order_networks`).
- **WiFi-модалка не закрывается кликом мимо окна.** `noCloseOverlay = true` —
  случайный клик по фону больше не уносит выбор сети и ход подключения (закрытие —
  кнопкой «Закрыть»).
- **Кнопка WiFi-списка: иконка вместо «!».** Кнопка `wifi-alert-btn` в правом
  углу заголовка «Устройства» показывает 📶 (счётчик новых сетей — число
  рядом с иконкой, подсветка при новых сетях/«панель в гостях» — без изменений).
- **Текущая сеть WiFi — в заголовке «Устройства».** После «💡 Устройства» в
  скобках выводится SSID, к которому подключена панель (`connected` из
  SSE `/devices/wifi`); до первого кадра потока скобки скрыты.
- **Модалка ввода пароля для защищённой сети.** Кнопка «Подключиться» у сети
  с `secured = true` (кроме уже активного подключения) открывает отдельную
  модалку «🔒 Пароль сети»: поле ввода и три кнопки — 🔒 показать/скрыть пароль,
  «!» вставить пароль по умолчанию `12341234`, 📁 выбор пароля из существующих —
  проекты (`myProfile.json` → `iotmSettings.apssid/appass`) и устройства
  (`settings.json` из RAM/FS → `apssid/appass`), новый эндпоинт
  `GET /api/devices/wifi/passwords` (`{platformio, projects, devices}` →
  `{label, ssid, pass}`; «PlatformIO» — первой строкой, до группы «Проекты»).
  После отправки панель возвращается к списку сетей, где видны стадии и ошибки
  подключения; открытая сеть и уже активное подключение — без модалки пароля
  (рабочий профиль не перезаписывается). Старое inline-поле пароля в модалке
  списка сетей убрано.
- **Подсказка при малом числе сетей.** Прежнее длинное предупреждение о переходе в
  подсеть модуля заменено: если в эфире меньше двух сетей, под списком выводится
  «Попробуйте обновить список сетей WiFi вручную средствами операционной системы.»
- **Устройство из AP модуля: имя/id из `settings.json`, папка `<name> <id>`.**
  `add_device_by_ip()` берёт имя и id из `settings.json` (прошивка всегда пишет туда
  `name` и `id` = `getChipId`) и читает его с повторами
  (`fetch_identity_with_retry`, `AP_IDENTITY_ATTEMPTS` × `AP_IDENTITY_DELAY`): сразу
  после ассоциации модуль отвечает не с первого раза. Папка формируется по ключу
  `<name> <id>` — как у устройств, найденных multicast-пакетом; папка «по IP» больше
  не создаётся (`/devlist.json` — лишь запасной источник имени/id, папка по адресу
  остаётся только для ESP-редактора ФС, `kind = esp`). Подключение к обычной сети
  (адрес панели вне `192.168.4.0/24`) больше не показывается как ошибка — просто
  устройство не добавляется. Документация — `docs/reference/magiciotm-api.md`.

- **Исправлено: WiFi-профиль отвергался (`0x80001 … profile is corrupted`).**
  Профиль задавал ключ устаревшим элементом `<keyM><key index="1" …/></keyM>`,
  который для схемы `WPA2PSK` недействителен — `netsh wlan add profile` возвращал
  «Недопустимый профиль для данной схемы. The network connection profile is corrupted»,
  и подключение к защищённой сети (в т.ч. к точке доступа модуля) не выполнялось.
  Ключ теперь записывается современным `<sharedKey><keyType>passPhrase</keyType>…`,
  а не-ASCII SSID дополнительно задаётся байтами в `<hex>` (иначе профиль тоже
  отвергается). Проверено на живом `netsh`: открытая сеть и WPA2-PSK (ASCII и
  не-ASCII SSID) добавляются без ошибок.

### Прошивка

- **Сборка bk7231n (LibreTiny) снова работает: `pio run -t buildfs` и `pio run`.**
  Шаг buildfs падал ещё до компиляции:
  `TypeError: Library.__post_init__() missing 1 required positional argument: 'env'`
  в `~/.platformio/platforms/libretiny/builder/utils/libs-queue.py` — builder-скрипт
  платформы объявляет поле `env: InitVar[Environment]`, но `dataclasses` не
  распознавал его как `InitVar`, и сгенерированный `__init__` вызывал
  `self.__post_init__()` без аргумента. Локально в файле платформы поле `env`
  сделано обычным, а `__post_init__()` — без аргументов (берёт `self.env`);
  функционально это эквивалентно и не зависит от причины, почему `InitVar`
  не распознался. Правка лежит вне репозитория и будет затёрта при обновлении
  платформы (откат — `git -C ~/.platformio/platforms/libretiny checkout --
  builder/utils/libs-queue.py`, после чего правку нужно наложить заново).
- **LibreTiny: блок настройки i2c-шины больше не ломает компиляцию.** `src/Main.cpp`
  объявлял дефолты `pinSCL = SCL, pinSDA = SDA`, но для `LIBRETINY` `Wire.h` не
  подключается и макросов `SCL`/`SDA` в Arduino-ядре нет — `error: 'SCL' was not
  declared in this scope` (регрессия после коммита с защитой i2c от мусорных пинов,
  проверенного только на ESP32-C6). Блок обёрнут в `#ifndef LIBRETINY`: вызовы
  `Wire.*` там и так были только под ESP32/ESP8266.
- **bk7231n больше не тянет `ESPAsyncWebServer`.** Зависимость приходила из общего
  `[common_env_data].lib_deps_external`, хотя для `LIBRETINY` асинхронный
  веб-сервер запрещён (`#error` в `include/Const.h`), а `lib_compat_mode = off`
  заставлял собирать её всегда — падало на `using ::emptyString;`
  (`literals.h`): глобального `emptyString` в Arduino-ядре LibreTiny нет.
  Список разделён: `lib_deps_external_base` (ArduinoJson, PubSubClient) — для всех
  платформ, `ESPAsyncWebServer` остаётся только в ESP-окружениях.

## [2026-09-30]

### Панель magicIoTm

- **WiFi-антенна: поиск точек доступа модулей.** Фоновый поток (`core/wifi.py`)
  сканирует эфир сразу после старта панели, дальше — раз в минуту
  (`netsh wlan show networks mode=bssid`, Linux-резерв —
  `nmcli`) и отбирает сети с префиксом `iotm` — AP-режим прошивки
  (`src/utils/WiFiUtils.cpp`, адрес модуля 192.168.4.1). В правом углу шапки списка
  устройств стоит кнопка «!» — она всегда видима (доступ к списку AP-сетей не должен
  зависеть от состояния сканера) и получает счётчик новых сетей и подсветку, когда
  такая сеть появилась или панель «в гостях»; клик по ней открывает модалку со
  списком AP-сетей (сигнал, канал, тип защиты, текущее
  подключение). Разбор вывода `netsh` не зависит от локали: ключи `SSID`/`BSSID` не
  переводятся, сигнал ищется по значению «NN%», канал/аутентификация — по синонимам,
  декодирование — UTF-8 → OEM-кодировка консоли → cp1251.
- **Подключение к AP модуля и добавление устройства.** По кнопке «Подключиться»
  панель в отдельном потоке создаёт WiFi-профиль (открытая сеть — `open`, иначе
  `WPA2PSK`/AES), подключается через `netsh wlan connect`, ждёт ассоциации (25 с),
  проверяет, что её адрес попал в подсеть модуля `192.168.4.0/24`, пингует
  `192.168.4.1` (до 3 попыток) и вызывает `add_device_by_ip()` — устройство
  появляется в дереве по SSE `/devices/stream`. Ход стадий виден в модалке, итог —
  в тосте. Новые эндпоинты: `GET /api/devices/wifi`, `GET /api/devices/wifi/stream`
  (SSE), `POST /api/devices/wifi/scan`, `POST /api/devices/wifi/seen`,
  `POST /api/devices/wifi/connect`, `POST /api/devices/wifi/return`; состояние —
  `_wifi_scan_state` /
  `_wifi_connect_state` в `state/globals.py`. Описание и формат кадров —
  `docs/reference/magiciotm-api.md`. Сканирование эфира приостанавливается на время
  подключения, чтобы не мешать ассоциации.
- **Возврат в домашнюю сеть («🏠 Домашняя сеть»).** Перед переходом в AP модуля (и при
  каждом скане) панель запоминает последнюю обычную сеть — поле `home` состояния
  сканера. Пока текущее подключение не совпадает с ней, кнопка «!» подсвечивается, а
  в модалке появляется кнопка возврата: `POST /api/devices/wifi/return` отключается от AP
  и подключается к сохранённому профилю (`netsh wlan disconnect` + `netsh wlan connect`),
  пароль не требуется, повторный профиль не создаётся.
- **Исправлено: устройство модуля в режиме точки доступа оставалось серым.** Свежий
  модуль отдаёт пустые `name`/`id` (и в `/devlist.json`, и в `settings.json`), поэтому
  папка создавалась по IP (`192.168.4.1 192.168.4.1`), а проверка идентичности искала
  ключ `unnamed <ip>` и не совпадала никогда — FSM держал серый статус при успешном
  пинге. Теперь кандидаты ключа безымянного устройства строятся от IP (вариант
  `unnamed <ip>` оставлен для совместимости) — устройство, найденное WiFi-антенной,
  становится зелёным; в журнал добавлена строка с полученными именем/id
  (`Ping OK, no identity confirmation: …, reported name/id: …`). Правила —
  `docs/reference/device-status-fsm.md`. Попутно: папка безымянного устройства
  (`<ip> <ip>`, в том числе легаси `unnamed <ip>`) в дереве устройств теперь
  подписывается просто IP — ключ и папка на диске не меняются.
- **Диагностика пустого списка AP-сетей.** «Списка iotm* нет» и «скан не работает»
  выглядели одинаково, хотя это разные проблемы. В состояние сканера добавлено поле
  `total` — общее число сетей в эфире: `total > 0` при пустом `networks` значит, что
  эфир виден и модуль просто не в режиме точки доступа (выключен либо уже в домашней
  сети), `total = 0` — не сканируется (WiFi выключен, netsh недоступен). Модалка и
  журнал теперь говорят это прямо: `WiFi-скан: AP-сетей iotm* не найдено (в эфире
  всего сетей: N, например: …)`.
- **Активный поиск эфира через `WlanScan`.** `netsh wlan show networks` не инициирует
  поиск — печатает кэш драйвера, который Windows обновляет сама и нерегулярно (на
  практике список мог оставаться пустым по несколько минут). Панель теперь перед
  чтением вывода пытается запустить сканирование через WLAN API (`wlanapi.dll`,
  ctypes — без внешних пакетов): `WlanOpenHandle` → `WlanEnumInterfaces` (интерфейс
  в состоянии `connected`) → `WlanScan` → пауза 2.5 с на обновление кэша → `netsh`.
  Кнопка «Обновить» (`POST /api/devices/wifi/scan`) сканирует принудительно. Если
  WlanScan недоступен или отказал (типичный код `87` = `ERROR_INVALID_PARAMETER` —
  наблюдается на части машин), после трёх отказов попытки прекращаются с
  предупреждением в журнале, и панель работает как раньше, читая кэш netsh.
  Причина отказа `WlanScan` — не права и не панель: на машине с «мёртвой» службой
  автонастройки `WlanEnumInterfaces` не отдаёт размер буфера, и WLAN API отказывает
  целиком. Лечится перезапуском службы (нужны права администратора) — после него
  `netsh` снова показывает весь эфир. Практический признак: `netsh wlan show
  networks` возвращает одну сеть (текущую) минутами подряд. Лечение:
  `Restart-Service WlanSvc -Force` (затем `Start-Service NlaSvc`) в PowerShell от
  администратора.
- **Исправлено: папка «по IP» оставалась серой, а модуль заводил папку-дубль.**
  Устройство в AP-режиме отдаёт имя и id (`IoTmanagerVer4` и id из `getChipId()`), но
  discovery создал для него папку `192.168.4.1 192.168.4.1`, ключ которой не совпадал
  ни с одним кандидатом, — FSM держал серый статус при успешном пинге, а первый же
  multicast-пакет создавал вторую папку. Добавлен `resolve_identity_folder`: папка «по
  IP» **усыновляет** настоящие имя/id (пишутся в `.device.json`), а папка с тем же
  именем и «переехавшим» id (у части прошивок id = `getChipId()` и меняется при
  перезагрузке) обновляется на месте — ключ и каталог на диске не меняются, иначе на
  каждый ребут появлялась бы новая папка. Папка на том же IP с другим именем не
  перезаписывается; мультикаст подтверждает усыновившую папку, а не создаёт дубль.
  Правила — `docs/reference/device-status-fsm.md`.
- **Исправлено: дубль состояния multicast-устройств в `core/devices.py`.** Модуль
  определял `_devices = {}` и `_device_thread = None` поверх импорта из
  `state/globals.py`, поэтому `routes/devices.py` (удаление устройства → `_devices.pop`)
  работал с другим словарём, чем multicast-слушатель. Тем же способом перекрывался
  `_fetch_progress` (`core/devices.py`): прогресс скачивания, который пишет
  `routes/devices.py`, не был виден `_device_busy_fetching()`, то есть пауза пинга и
  WS-запросов на время `fetch` фактически не работала. Обе локальные копии удалены,
  остался единый источник истины; на месте — поясняющие комментарии.

- Исправлено «ESP-устройство не обнаружено» для плат с нативным USB
  (ESP32-S2/S3/C3): `esptool flash_id` на портe приложения (например COM6)
  сбрасывает чип в режим загрузки с переименованием порта (COM6 -> COM7), из‑за
  чего `detect_device` падал с `OSError(22, 'Invalid argument')`. Теперь после
  неудачи ищем переименованный COM‑порт того же USB‑устройства (по

  отследить переименование COM7→COM6 на Windows. `list_esp_ports` и
  `list_raw_ports` делают повторный опрос при пустом результате. Сообщение об
  ошибке уточнено (разные причины: порт не создаётся / чип не отвечает / семейство
  не совпадает).

- Исправлен сбой прошивки файловой системы (`pio run -t uploadfs`) с
  `warning: can't read source directory` и `*** [.pio\build\<env>\littlefs.bin] Error 1`:
  причина — устаревший путь `[platformio] data_dir` в `platformio.ini` проекта после
  переименования категории (`Test` → `Платы`) или переноса проекта; PlatformIO берёт
  этот путь как `$PROJECT_DATA_DIR` и передаёт его `mklittlefs -c`. Теперь:
  - `utils/projects.py` умеет читать/перезаписывать `data_dir` (только строку в секции
    `[platformio]`, остальной ini и комментарии не трогаются) и автоматически
    синхронизирует его при переименовании категории/проекта, переносе и копировании;
  - перед USB-прошивкой в режимах `fs`/`full` каталог данных сверяется с проектом:
    `POST /upload/start` возвращает `409` с `code: "data_dir"`, а UI показывает модалку
    «Исправить и прошить» (`POST /projects/repair-data-dir`) с повторным запуском;
  - `utils/flash.py` дополнительно проверяет каталог в воркере (понятная ошибка вместо
    «код 1») и после успешной прошивки обновляет `firmware.bin`/`littlefs.bin`
    в `iotm/<платформа>/400/` проекта.
- Добавлены тесты панели `tools/magicIoTm/tests/test_data_dir.py`
